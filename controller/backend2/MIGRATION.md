# Migration Notes: backend -> backend2

## What changed

- Full architectural rewrite from a single-file global-state backend into a layered service-based backend.
- Startup/shutdown moved to deterministic FastAPI lifespan handling.
- Camera capture moved to per-camera workers.
- Recording moved to queue + writer-thread pipeline.
- Calibration moved from runtime checkerboard solving to external `calib_out/final_calibration.json` consumption.

## Calibration model change

- `backend` mixed checkerboard capture, detection, and stereo solve into runtime APIs.
- `backend2` treats calibration as an external artifact generated by the separate calibration project.
- Relative transforms are computed from world poses in `final_calibration.json`.

## Operational impact

- Frontend routes remain unchanged.
- Existing calibration UI still functions, but capture/detect/perform routes are now compatibility wrappers.
- Readiness now explicitly depends on both camera availability and successfully loaded external calibration.

## Risks and tradeoffs

- If camera IDs in `final_calibration.json` do not match runtime camera IDs (`cam0`, `cam1`, ...), stereo endpoints will report missing calibration.
- Legacy checkerboard endpoints no longer represent true checkerboard detection quality.
- In-memory recording buffers can still grow for long sessions; queue architecture reduces lock contention but does not fully eliminate memory growth.
